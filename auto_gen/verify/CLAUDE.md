# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A UVM (SystemVerilog, UVM-1.2) chip verification environment for an SoC named `soc` (project id `PID 003`). The environment is largely **auto-generated** from JSON descriptions by Python scripts, then hand-extended. There are per-module UVCs (`reg`, `jls`, `ro`, `uart`, `efuse`), a top-level env that assembles them, and a shell/Makefile flow (`wsim`) that drives Synopsys VCS + Verdi, with LSF (`bsub`) dispatch and DPO support.

This working directory (`auto_gen/verify`) is one of two verification trees in the repo; `../../legecy/` holds an older tree that the auto-gen flow is replacing. Prefer this tree.

## Commands

Compilation and simulation run on Linux with VCS/Verdi/LSF — **not on this Windows dev box**. `wsim` is the single entry point; it generates the RAL model, expands the test list from JSON, then compiles and simulates each case in `sim/uvm_scratch_*/` scratch dirs.

Run from `sim/` (where `wsim` and `project_name` are deployed by `file_manage.sh`):

```bash
./wsim -c reg_smoke_test -uvm            # run one test case
./wsim -c reg_smoke_test -uvm -fsdb      # + dump FSDB waveform (forces iteration=1)
./wsim -c reg_smoke_test -seed 12345     # fixed seed (default: random)
./wsim -m reg                            # run all tests for module 'reg'
./wsim -smoke | -stage1 | -stage2 | -full   # regression groups (from case JSON flags)
./wsim -l gate|post -corner typ|bst|wst  # gate/post-layout sim with SDF
./wsim -cm                               # enable code coverage
./wsim -gui                              # launch Verdi GUI
./wsim -h                                # full option list
```

Pass/fail is decided by grepping `UVM_ERROR`/`UVM_FATAL` counts in `sim.log`; results roll up into `result.txt` and re-run commands for failures land in `fail_wave.txt`. The Makefile (`tb_top/scripts/Makefile`, source in `script/sflow/Makefile`) builds the actual `vcs`/`simv` command lines from `wsim`'s options; look there to understand what a given switch expands to.

## Regenerating the environment

The SV files are templates emitted by Python. **Editing generated files by hand is normal**, but know that a regeneration can overwrite them (`gen_uvm_env.py` respects existing files unless `--overwrite` is given).

```bash
# from script/
python gen_uvm_env.py --gcfg                          # emit a config template (uvm_env_config_template.json)
python gen_uvm_env.py -c uvm_env_config_template.json --guvc [--overwrite]  # generate all UVCs + base_seq + base_test
python gen_uvc.py -n <name> -o <dir> [-t <bus_type>]  # generate a single UVC (adapter only if -t given)
```

- `script/uvm_env_config_template.json` is the **source of truth** for which modules exist and their attributes (`is_active`, `enable_adapter`, `adapter_type`, `has_interface`, `has_tb_top`). Add a module here, regenerate, then wire it into filelists.
- `script/file_manage.sh` (Linux / Git Bash / WSL) or `script/file_manage.ps1` (native Windows) deploys the flow files out of `script/` into their runtime locations (`sim/`, `tb_top/scripts/`). Both are script-relative (runnable from any cwd) and do the same copies. Run one after changing `wsim`/`Makefile`/`testjson2lst.py` under `script/sflow/`.
- The RAL model (`verify/ral/ral_reg_model.sv`) is generated by `wsim`'s `RalGen` step from `hdl/common/reg_table/reg_table_reg_list.csv` via `utils/reg/gen_reg_model.py` — it is regenerated automatically when the CSV or script changes.

## Test case definition (JSON → test list)

Test cases are **not** enumerated in SV. They live in `json/case/<module>.json`, indexed by `json/module.json`. `tb_top/scripts/testjson2lst.py` (source `script/sflow/testjson2lst.py`) reads these plus the chip define file and emits a `.list` that `wsim` iterates.

Each case entry carries: regression-group booleans (`stage1`/`stage2`/`smoke`/`full`), `iteration`, `UVM_TESTNAME` (the actual `+UVM_TESTNAME` — note the JSON *key* is a logical case name that can differ from `UVM_TESTNAME`), `VCS_MACRO_OPT` (compile `+define+`s), and `VCS_PLUSARGS_OPT` (runtime `+plusargs`). Global/UVM-wide macros live in `json/module.json`. To add a test: add an entry to the module's case JSON — do not hand-edit list files.

## Architecture

**UVC pattern (per module, under `uvc/<name>/`).** Every UVC is generated to the same shape by `gen_uvc.py`: `src/` holds `*_agent`, `*_driver`, `*_monitor`, `*_scoreboard`, `*_coverage`, `*_sequencer`, `*_sequence_item`, `*_item`, `*_coverage_item`, `*_base_cfg`/`*_cfg`, `*_if`(+`*_if_pc` for props/cover), and optionally `*_reg2<bus>_adapter`; `env/` holds `*_env` + `*_pkg` (the include manifest); `script/uvm.f` is the compile filelist. Monitors/scoreboards extend the shared `base_*` classes in `utils/base_uvc/`. When adding signals or logic, follow the generated skeleton — e.g. a new interface signal must be added in `*_if.sv`, sampled in the monitor, and covered in `*_coverage.sv`.

**Top assembly.** `env/top_env.sv` instantiates every `*_env`, sets `drv_is_active = UVM_ACTIVE` on the active ones, builds the virtual sequencer `top_virtual_sequencer` (`env/top_vseqr.sv`) and connects each module sequencer into it, and builds/locks the RAL model (`ral.set_hdl_path_root(...)` points into the DUT hierarchy). `env/top_pkg.sv` is the top include manifest; `env/top_if.sv` the top interface.

**Test/sequence base.** `test/base_test.sv` and `seq/base_seq.sv` are the generated bases that declare a handle + virtual interface + base_cfg for **every** module and fetch them from `uvm_config_db`. Per-module tests (`test/<mod>_test.sv`) and sequences (`seq/<mod>_seq.sv`) extend these. `base_test` uses the full UVM runtime phase set (reset/configure/main/shutdown) with objections; put reset in `reset_phase`, register/warm-up init in `configure_phase`, stimulus in `main_phase`. Shared per-module sequence helpers live in `seq/comm_<mod>_methods.sv` and are `` `include ``-d into `base_seq`.

**Config & runtime toggles.** `base_cfg` objects are created and `uvm_config_db`-set in `base_test.build_phase`, then randomized in `start_of_simulation_phase`; `set_<mod>_cfg_type()` does type overrides. `utils/global_pkg.sv` declares string-keyed associative arrays (`MON_CHECKS_ENABLE`, `SB_CHECKS_ENABLE`, `IF_CHECKS_ENABLE`, `MON_COVERAGE_ENABLE`, `IF_COVERAGE_ENABLE`) that gate checkers/coverage at runtime; `base_test::set_*_enable()` are the accessors.

**Interface connection.** `intf/*_if_conn*.sv` bind UVC interfaces to the DUT; `*_gpls.sv` variants are for gate/post-layout (netlist) simulation. `tb_top/tb_top/tb_top_<scope>.sv` are the sim top modules; `tb_top/filelist/*.f` select RTL vs. gate vs. IP sources per sim level.

**Filelist layering.** `tb_top/filelist/uvm.f` is the UVM env filelist: base pkgs (`global_pkg` → `reg_mdl_pkg` → `ral_reg_model` → `base_uvc_pkg`) first, then each UVC's `uvm.f`, then `tb_top_soc.f` and `top_pkg.sv`. Package/include ordering matters in SV — respect the existing order when adding files.

## Conventions

- Naming is strict and load-bearing: a module `foo` implies class prefix `foo_`, package `foo_pkg`, interface `foo_if`, config-db keys `foo_vif`/`foo_cfg`, macro guards `__FOO_*__`. The generators assume it; keep it.
- Block-level vs. system-level sim is selected by a `+define+<MOD>_BLOCK_TEST` macro (see `Makefile` `block_env` and `uvm_blk_*.f` filelists) — block tests use different filelists and register-init config.
- Filelist paths are relative to the scratch run dir and use the `../../../../verify/...` prefix; keep that when editing `.f` files.
- Some scripts hardcode a site Python (`python3.6`, `/opt/anaconda3/bin/python`) and LSF queue/host names — these are environment-specific.
