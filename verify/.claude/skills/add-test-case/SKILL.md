# Add Test Case

Generates a new leaf test case for one module, synchronizing the three places a test case lives: the `test/` class, the `seq/` class and the `json/case/<mod>.json` entry - following this repo's inheritance rules and naming convention. The valid modules are the keys of `json/module.json` (regenerated by every `--guvc`), so this skill needs no change when modules are added or removed. Read `test_case_dev_manual.md` (in this skill directory) first if you haven't worked in this tree before; this skill automates exactly the mechanical steps that manual describes in its §3/§4.

Paths below are relative to `verify/` (the "verify root").

## Run this — the driver

```bash
${CLAUDE_SKILL_DIR}/add_test_case.py \
  --module <mod> \
  --function <short_scenario_name> \
  --level <system|block> \
  [--stage1 true|false] [--stage2 true|false] [--smoke true|false] [--full true|false] \
  [--iteration N] [--codecoverage true|false] \
  [--macro-opt "+EXTRA_DEFINE"] [--plusargs-opt "+EXTRA_PLUSARG"]
```

Examples:

```bash
# system-level
${CLAUDE_SKILL_DIR}/add_test_case.py \
  --module <mod> --function toggle_check --level system --stage1 true --smoke true

# block-level (the module needs its block base pair - see Gotchas)
${CLAUDE_SKILL_DIR}/add_test_case.py \
  --module <mod> --function burn_and_read --level block --stage2 true --iteration 4

# block-level with an extra compile define for this case only
${CLAUDE_SKILL_DIR}/add_test_case.py \
  --module <mod> --function wait_states_block --level block --macro-opt "+<EXTRA_DEFINE>"
```

The script prepends `+<MOD>_BLOCK_TEST` to a block-level `VCS_MACRO_OPT` itself, so `--macro-opt "+X"` gives `+<MOD>_BLOCK_TEST+X`.

This creates, per the naming rule `<mod>_<function>_test` / `<mod>_<function>_seq`:

- **System level**: appends `<mod>_<function>_test extends <mod>_base_test` into `test/<mod>_test.sv`, and `<mod>_<function>_seq extends <mod>_base_seq` into `seq/<mod>_seq.sv`. The test's `main_phase` starts the sequence on `vseqr_h.<mod>_seqr_h` (the module's sub-sequencer on `top_virtual_sequencer`).
- **Block level**: appends `<mod>_<function>_test extends <mod>_block_base_test` into `test/<mod>_block_base_test.sv`, and the seq analog into `seq/<mod>_block_base_seq.sv`. The test starts the sequence on `<mod>_env_h.vseqr_h` (the module env's own sequencer).
- Either way: a new entry keyed `"<mod>_<function>_test"` in `json/case/<mod>.json`'s `"tests"` object, with `UVM_TESTNAME` set to the same class name, and - for block level - `VCS_MACRO_OPT` prefixed with `+<MOD>_BLOCK_TEST`.

The script refuses (clear error, no partial edits) if: the module is not in `json/module.json`, `--function` isn't a valid identifier fragment, the class name already exists in the target file, the JSON key already exists, or - for block level - the module has no block base pair yet.

## After running

The generated seq's `body()` is a `// TODO: real stimulus...` stub. Fill it in, then from the repo-root `sim/`:

```bash
./wsim_oeda -c <mod>_<function>_test -seed 1     # local oEDA run
./wsim -c <mod>_<function>_test                  # VCS (sign-off flow)
```

A clean run (no `UVM_ERROR`/`UVM_FATAL`) doesn't mean much until the scoreboard has a real check — see `test_case_dev_manual.md` §5.

## Gotchas

- **Block level needs a block base pair**: `test/<mod>_block_base_test.sv` + `seq/<mod>_block_base_seq.sv` + `tb_top/filelist/uvm_blk_<mod>.f`. `--guvc` generates them for a module with `has_tb_top: true`; the flow scripts derive the filelist from the `<MOD>_BLOCK_TEST` define, so no per-module flow branch is needed. Which modules have block support today: the §0 table of `docs/memory/arch_memory.md`.
- **Follow the module's existing naming**: if the module's block tests are named `<mod>_<fp>_block_test`, pass `--function <fp>_block` (the script builds `<mod>_<function>_test`). Module-specific helpers and quirks (e.g. sequence helpers that must `get_response`) are in `docs/modules/<mod>.md`.
- **`stage1`/`stage2` default to mutually exclusive**, matching the existing entries (smoke tests are `stage1`-only, regression tests `stage2`-only). If you pass one, the script infers the other. Pass both explicitly to put a test in both groups.
- **The target `json/case/<mod>.json` is fully re-serialized** (Python `json`, 4-space indent) when an entry is added - semantically identical, formatting normalized. Expected.
- **Duplicate-safe, not idempotent**: running the same `--module`/`--function`/`--level` twice fails on the second run instead of overwriting.
- **No new files are created for leaf classes** - the script appends into the existing per-module file, which is already `` `include ``-d by `env/top_pkg.sv` (system tests), `seq/chip_sequence_lib.sv` (system seqs) or the block `.f` filelist (block level).

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `ERROR: --module must be a module of json/module.json` | module not in the generated index | check the name; a new module needs the config + `--guvc` first (json2env) |
| `ERROR: Module '<mod>' has no block-level base yet` | `--level block` for a module without block support | regenerate with `has_tb_top: true` (json2env), or use `--level system` |
| `ERROR: Class <name> already exists in <file>` | re-ran with the same `--module`/`--function`/`--level` | pick a different `--function`, or edit the existing test |
| `ERROR: Test key <name> already exists in <json file>` | same, JSON side | same fix |
| `ERROR: --function must be an identifier fragment...` | spaces, hyphens, or a leading digit | use `snake_case`, e.g. `write_read` |
